# T3: keyboard-first setup, Weather cities, crash evidence, icon audit

Branch `q25/t3`. Covers the remaining T3 items of
[`../SABLEOS_GAP_REVIEW.md`](../SABLEOS_GAP_REVIEW.md): IR-014, IR-015, #84
and #83. Branding and density belong to KF-B and are not here.

Nothing here has run on a phone. The Android/Compose code and the
LineageOS patches have not been compiled (no Android SDK, Gradle or AOSP tree
here). The pure Kotlin/Java logic is unit-tested off-device; the shell tools
are tested with fakes in `tests/run.sh`.

## 1. IR-014: keyboard-first LineageOS setup

LineageOS 23.2 ships `LineageSetupWizard` from
`LineageOS/android_packages_apps_SetupWizard` (tree path
`packages/apps/SetupWizard`), not GrapheneOS SetupWizard2. The
keyboard-first reference model (`sable-src/reference/sable-setup-keyboard-first-flow`)
is ported into it as two framework patches, base
`715b772f07c52ce0fdb83b9891765f3de992ffb5` (lineage-23.2):

| Patch | What it does |
|---|---|
| `patches/framework/packages/apps/SetupWizard/0401-SableOS-keyboard-first-focus-in-setup-steps.patch` | `BaseSetupWizardActivity.dispatchKeyEvent` runs every key through `sable/SableKeyFocus` (view side) and `sable/SableKeyPolicy` (pure). With nothing focused, the first arrow/Tab/Enter/Space focuses the step's first text field, else its primary action (Welcome's Start, else Next), else its first control, using `requestFocusFromTouch` so the focus highlight shows. MoveHome/MoveEnd go to the first/last control outside text fields. A held Enter/Space/Tab does not repeat. Enter in a step's last text field runs the primary action. Every other key (arrows and Tab between controls, Enter/Space on a button, Back, Escape, which the platform key map turns into Back, text and cursor keys in a field, system Home, PageUp/PageDown, Ctrl/Meta shortcuts) keeps its platform behaviour. Any exception falls back to platform handling. |
| `patches/framework/packages/apps/SetupWizard/0402-SableOS-Sable-Keyboard-readiness-step-before-Wi-Fi-a.patch` | New `SableKeyboardActivity` step, inserted after Locale in `lineage_wizard_script.xml` (owner only), before SIM, Wi-Fi and screen lock. It reads whether Sable Keyboard (`org.sableos.titan2.keyboard/.android.SableImeService`) is installed, enabled and selected (`InputMethodManager`, `Settings.Secure.DEFAULT_INPUT_METHOD`), says so, and offers one fix: Sable Keyboard settings when it is selected, the input-method picker when it is enabled but another keyboard is selected or the state is unknown, input-method settings when it is not enabled, nothing when it is not installed. Offers are shown only if they resolve. It writes no setting; Next is always enabled. If the step's intent cannot be resolved, WizardManager skips it. |

The two patches touch disjoint files, so `apply-framework-patches.sh apply`
(which checks every patch against the unpatched tree before applying any)
accepts them. Both were checked with `git apply --check` and
`--reverse --check` against the base commit.

**Text entry for critical fields.** The Wi-Fi password and the screen-lock
PIN are entered in Settings screens (`android.settings.NETWORK_PROVIDER_SETUP`,
`com.android.settings.SETUP_LOCK_SCREEN`) that LineageSetupWizard opens, not
in the wizard. Hardware keys reach those fields through the selected IME. At
Q4 Sable Keyboard is the only IME (it overrides LatinIME). Its existing
`FieldPolicy`/`Resolver` handle password fields and type digits from letter
keys in numeric fields (`numericAutoAlt`, on by default). The readiness step
makes sure the user knows this before those screens and can fix the
selection. No Settings patch was needed for that.

**Hand-off to Sable Setup.** The reference says Sable Setup
(`apps/titan2/platform/setup`) is a post-provisioning readiness helper, not
part of the setup flow. So the wizard does not launch it. The readiness step
only says that Sable Setup checks keyboard and home defaults after setup.
Launching a helper app from inside the wizard could leave setup unfinished,
which the brief forbids.

**Never uncompletable.** The focus helper only adds focus moves, one guarded
primary action and swallowed key repeats. It never claims Back or Escape and
falls back on any error. The readiness step keeps Next enabled in every state,
and if it cannot be resolved the wizard skips it.

Reference markers covered by code and pure tests:

| Reference key | Status |
|---|---|
| P3_KEYBOARD_FIRST_SETUP_MODEL, P3_MOVE_HOME_MOVE_END_NAVIGATION, P3_NORMALIZED_KEY_VOCABULARY | Code + tests (`SableKeyPolicyTest`) |
| P3_SOFTWARE_KEYBOARD_FALLBACK | Code + tests (`SableKeyboardStateTest`: offers, `showSoftOnFocus`) |
| P3_SIM_STEP_NON_DEAD_END | Unchanged LineageOS behaviour: `SimMissingActivity` always has Next. The SIM/radio state never gates completion. |
| P3_WIFI_TEXT_ENTRY_MODEL | Settings Wi-Fi dialog + Sable Keyboard. Device check needed. |
| P3_ACCOUNT_TEXT_ENTRY_MODEL | No account step in LineageOS without GMS. Not applicable. |
| P3_SQUARE_LAYOUT_MODEL | The readiness page scrolls, uses 48dp targets and no horizontal scroll. Other pages are stock GLIF. Check at 720x720 on the device. |
| Focus visible after key / hidden after touch | Platform touch mode: `requestFocusFromTouch` leaves touch mode, and a touch re-enters it. |
| Device runtime (first boot, factory reset) | Needs the device. |

## 2. IR-015: Weather user-managed cities and per-city cache keys

Ported from `sable-src/reference/sable-weather-cities` into canonical
`sable-src/apps/r8/android/weather`.

Pure layers (no android imports, JUnit tests in `src/test`):

| File | Role |
|---|---|
| `cities/Cities.kt` | `City`, validation, `DefaultCities` (the four canonical built-ins), `CityState` add/remove/select/reset. Ported as is. |
| `cities/CityStore.kt` | Versioned codec and `CityRepository` over `KeyValueStore`. `KeyValueStore` gains default `remove`/`keys` for cache pruning. |
| `cities/StartLiveRefresh.kt` | `cacheKey(city)` = `lat,lon,timezone`, `cacheValidFor`, `needsRefresh`. Ported as is. |
| `cities/ForecastCache.kt` | **Per-city cache.** One entry per city under `forecast_v1:<cacheKey>`. The entry repeats its key, and `read` returns it only when `cacheValidFor` matches the active city. `retainOnly` drops entries of removed cities. `LegacyWeatherCache.migrate` moves from the old single `protocol`/`observed_epoch_seconds`/`location_name` layout. It keeps the old selection and drops the old forecast, because its city cannot be known: `location_name` was written before every fetch, even failed ones. |
| `cities/CityCatalog.kt` | Offline add-city search: 65 built-in cities plus manual `Name, lat, lon, Area/Zone` entry. No geocoding or network. |
| `cities/CityKeys.kt`, `input/KeyInput.kt` | Keyboard model of the city screen and the normalized key mapper. Ported. |
| `WeatherModels.kt` | `DefaultWeatherLocations` is now derived from `DefaultCities`, plus `City`/`WeatherLocation` conversions. |

Android side (uncompiled):

* `WeatherRepository`: the forecast cache is per city (`ForecastCache`). The
  city list and selection come from `CityRepository`, and the migration runs
  in `init`. `afterCityEdit` prunes caches and calls `notifyChange` on the
  Start/Live snapshot URI whenever the active city changes. Before, that only
  happened after a successful fetch. `PreferencesStore` reads through
  `SharedPreferences.getAll()`, so the old long-typed key reads back without a
  `ClassCastException`.
* `WeatherSnapshotProvider` is unchanged. It calls `load()`, which now shows
  only the active city's own forecast.
* `CitiesSection.kt`: the new "cities" section replaces the fixed location
  list. Rows select, "remove" asks for confirmation, "add city" opens the
  search with offline results, "reset to built-in cities" asks for
  confirmation. Keys are driven by `CityScreenModel` through `KeyMapper`.
  Text keys in the search field go to the field. Back/Tab leave the section.
  Every item is also a touch target.
* `MainActivity`: a forecast that arrives for a city the user has since left
  is not shown under the new city's name.
* `build.gradle.kts`: `testImplementation("junit:junit:4.13.2")`, as in the
  hub, messages and design modules.

Reference keys: P4_USER_ADD_CITY, P4_USER_REMOVE_CITY, P4_CITY_PERSISTENCE,
P4_SELECTED_CITY_PERSISTENCE, P4_RESET_DEFAULTS,
P4_MANUAL_CITY_PRECISE_LOCATION_REQUIRED=NO, P4_KEYBOARD_FIRST_CITY_MANAGEMENT,
P4_START_LIVE_REFRESH_CONTRACT, P4_MOVE_HOME_MOVE_END_NAVIGATION and the
reference's "cache per city" handoff step are covered by code and pure tests.
On-device behaviour (Compose focus, Start/Live refresh in Sable Start) needs
the device. The manifest's `ACCESS_COARSE_LOCATION` is a canonical decision
and is left as is.

## 3. #84: first-run crash evidence

`scripts/capture-crash-evidence.sh` is documented in
[`../CRASH_EVIDENCE.md`](../CRASH_EVIDENCE.md). It is read-only over adb and
captures in this order: logcat crash and other buffers, DropBox crash, ANR,
tombstone, watchdog, boot and WTF tags, `exit-info` (global and per Sable
package), `getprop`, tombstone and ANR listings (pulled when readable), Sable
package versions, `SUMMARY.txt`, `INDEX.tsv` and `SHA256SUMS.txt`. It writes
a timestamped `chmod 700` folder, refuses an output inside the repo, and
needs exactly one device or `--serial`. `SABLE_ADB` selects adb.
`tests/run.sh` runs it against a fake adb. The test fails if adb is called
with `-c`, `root`, `reboot`, `install`, `uninstall`, `clear`, `rm`, `wipe`,
`disable`, `push` or `-w`, if the hashes don't verify, or if the repo-path or
two-device cases are accepted. Not yet run on a Q25.

## 4. #83: static icon/launch audit

`scripts/audit-app-icons.py` (python3, stdlib only) audits every enabled row
of `product/q25/apps.tsv` from `sable-src` without building. It checks
launcher activities (an `<activity>` or `<activity-alias>` with MAIN and
LAUNCHER), the label (literal, `values/strings.xml` or a per-flavor Gradle
`resValue`), whether the icon resolves (flavor `res` first) and is not a
placeholder, round icon, adaptive icon, monochrome layer, extra launcher
entries and shared icons. Flavor apps (Mail, Text Reader) are checked through
what `apply_sable_flavor.py` writes.

`tests/run.sh` enforces launcher, label and icon (these pass for all 17
apps) and that no app has extra launcher entries. Round, adaptive and

Findings:

1. **Fixed:** Sable Keyboard put its diagnostic `KeyProbeActivity` ("Sable
   Key Probe") in the app drawer as a second launcher entry with the keyboard
   icon. The LAUNCHER category is removed. The probe now opens from a button in
   Sable Keyboard settings or with
   `adb shell am start -n org.sableos.titan2.keyboard/.android.KeyProbeActivity`.
2. **Open (design):** none of the 17 apps has an adaptive icon or a
   monochrome layer. Every icon is a full-bleed vector with a baked-in rounded
   square, and `roundIcon` is the same drawable. Android 13+ themed icons and
   the launcher's mask therefore don't apply. The SableOS R9 visual review
   (`sableos/docs/R9_DAILY_DRIVER_VISUAL_REVIEW.md`) says icons need an
   *approved* adaptive identity, and branding is KF-B's. So this was not
   generated here. Suggested mechanical route once approved, per app:
   `mipmap-anydpi-v26/ic_launcher_sable.xml` = `<adaptive-icon>` with
   background = the tile colour, foreground = the existing glyph group and rail
   in a 108dp viewport (viewport 384, content translated by 64, so the old
   256-unit art fills the 72dp safe zone), and monochrome = the glyph only.
   Point `android:icon`/`roundIcon` at it. Keep `@drawable/ic_sable_*` for
   in-app use, because Compose `painterResource` cannot draw an
   `<adaptive-icon>`.
3. **Open (minor):** Sable Mail's flavor doesn't set `android:roundIcon`.
   Upstream Thunderbird 23.0 has none either, so launchers fall back to the
   Sable icon. Harmless. Add it together with item 2.
4. **Not static:** warm/cold launch time and visible startup stalls need the
   device (#83 performance part). One candidate for review: Weather's
   `MainActivity.onCreate` runs `WeatherNative.selfTest()` synchronously and
   throws if it fails.
